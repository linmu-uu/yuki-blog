每次有人问"博客用什么搭比较好"，回答之前我都想先问一句：**你想要的是什么**。

因为所谓"选静态站点框架"，本质上是在同时回答三个问题：

1. **内容怎么写**——Markdown 还是别的？写完要不要检查字段？
2. **页面怎么拼**——能不能把侧边栏、卡片、组件抽出来复用？
3. **JS 什么时候进浏览器**——是默认全打包进去，还是按需加载？

这三件事的答案，决定了这个框架适不适合你。这篇横向对比几种主流选择，最后说说这个博客为什么是 Astro。

## 先看一张对比表

| 对比项 | Astro | Hugo | Hexo | 纯手写 |
| --- | --- | --- | --- | --- |
| 语言 / 运行环境 | Node + 各框架语法 | Go，单个二进制 | Node | 你自己 |
| 构建速度 | 快（本项目 17 页约 1.5s） | **极快**（几千页秒级） | 中等 | 取决于你写了多少 |
| 默认 JS 体积 | **几乎为零** | 几乎为零 | 看主题 | 你自己控制 |
| 组件复用 | ✅ 一等公民 | 模板/partial | 主题内模板 | 自己造 |
| 内容校验 | ✅ 内置 schema | 弱 | 弱 | 无 |
| 交互能力 | 岛式架构，可嵌 React/Vue/Svelte | 自己写 JS | 自己写 JS | 自己写 JS |
| 上手成本 | 中（要会一点 JS/TS） | 低（会 Markdown 就能发） | 低 | 高 |
| 适合 | 有个性化界面 + 一点交互的站点 | 内容为主、篇数很多 | 想要现成主题的博客 | 就想折腾 |

下面逐个说。

## 一、Hugo：为"快"和"零依赖"而生的那一套

Hugo 是 Go 写的，编译成一个可执行文件。它的最大卖点非常直白：**快**。

- 几千篇文章的站点，构建几秒钟就能跑完
- 没有 `node_modules`，一个二进制文件 + 一个内容目录就能跑
- 部署时甚至可以在 CI 里直接下载二进制执行，不用装整个前端工具链

缺点也来自同一个地方：模板是 Go 的模板语法，写起来没有组件那种"手感"；
遇到交互（搜索、播放器、评论）基本都要自己写 JS，然后手动塞进模板。

**如果你的博客是"就是写文章"，Hugo 是最省心的选择。**

## 二、Hexo：中文圈很成熟的那一套

Hexo 是 Node 生态里的老牌方案，主题多、插件多，中文教程也最齐全。

- 装完 `hexo init` 就有个能跑的博客，换主题就换一个文件夹
- 生态成熟：RSS、搜索、音乐播放器、留言板几乎都有现成插件

代价是它比 Hugo 慢，而且**主题定制往往要读主题自己的文档**——
你想改一个卡片，得先搞清楚这个主题的模板是怎么组织的，翻半天才知道该动哪个文件。

**如果你"只想快点有个博客"、"不打算大改样式"，Hexo 很合适。**

## 三、纯手写：从 HTML 到构建脚本都自己来

听起来很硬核，但"手写"有很多层次：可能只是写几个 HTML 页面；也可能是自己写一个构建脚本，
把 Markdown 编译成 HTML。

它的好处是**没有任何魔法**：产物完全可解释，依赖最少，改起来不需要先学一个框架。

代价是所有"框架顺手给你的东西"都要自己补：分页、标签页、RSS、站点地图、SEO meta、
代码高亮、搜索结果……每一个单项都不难，加起来是个不小的工程。

不过——**这个博客就用了一个"手写"的小工具**：站内搜索索引是[用 Lua 现写的](/posts/lua-search-index-tool/)。
所以"手写"也不一定是全盘手写，**可以只在框架不擅长的地方补一个自己的小脚本**。

## 四、Astro：默认零 JS，交互按需"岛"化

Astro 的核心卖点一句话就能说完：**页面默认是纯 HTML，需要交互的部分才单独加载 JS。**

这个模型叫"群岛架构"（Islands Architecture）。一个博客页面可能是这样：

```
静态 HTML：文章正文、卡片、页脚
岛 ①：音乐播放器（只有它需要 JS）
岛 ②：评论区（滚到附近才加载）
岛 ③：搜索框（在搜索页才加载）
```

好处是首屏极快——本博客首页一共约 145KB，其中 42KB 是壁纸，还要扣掉 Cloudflare 自动注入的
10KB 分析脚本，自家 JS 只剩二十来 KB。

另外三个能力是当初选它的关键：

- **组件化**：侧边栏卡片、文章卡片、日历这些都能写成组件复用，而不是复制 HTML
- **内容集合 + schema 校验**：front-matter 的字段在构建时就会校验，写错直接报错
- **视图过渡**：内置页面切换动画，不需要自己写一套路由

### 但它也不是没有代价

写了一整套主题之后，这三个坑印象最深：

**1. 作用域样式 + 动态注入会打架。**
Astro 的组件样式靠 `data-astro-cid-*` 属性作用域化，一旦你用 JS 的 `innerHTML` 重新渲染节点，
这些属性就没了，**样式会整块失效**。本博客的动态列表就踩过：拿到后端数据重绘之后，
卡片瞬间变成"没穿衣服"的样子。解决办法是重绘后把那个属性补回去。

**2. 内联脚本和页面生命周期要自己拿捏。**
模块脚本在切页时不会重跑，但 `astro:page-load` 会；组件里的内联脚本又要考虑执行顺序。
能跑通，但排错时要清楚"这段代码到底在什么时候执行"。

**3. 构建速度不上不下。**
比 Hugo 慢一截，比 Next.js 之类又轻不少。本站 17 个页面构建约 1.5 秒——
对个人博客完全够用，但如果你有上万篇内容，这个差距会变得明显。

## 五、这个站为什么最后是 Astro

说回这个博客本身。它不是从零开始的选型，而是一次**主题升级**：

最初用的是 Firefly 主题——一个 Astro 写的静态博客主题。用着用着想要更多东西：
动态、评论、音乐、会换壁纸的首页、跟着背景变的配色……于是决定自己写一套。

留在 Astro 的理由，按重要性排：

1. **迁移成本最低**。内容本来就是 Markdown，主题本来就是 Astro，不需要搬家
2. **这套界面非组件化不可**。侧边栏五张卡片、动态时间轴、日历、播放器，
   纯手写 HTML 会把自己写死；组件化之后改一处就全站生效
3. **要 JS，但不能多**。音乐、评论、搜索、动态、壁纸轮换都需要脚本，
   但首屏必须快。岛式架构 + 手动控制加载时机正好符合需求
4. **需要校验**。文章越来越多，front-matter 少写一个字段能在构建时炸出来，
   比线上发现"首页少了半句话"好得多
5. **视图过渡直接用**。页面切换动画是这套主题体验的一部分，Astro 内置了

一句话总结：**要组件、要少量 JS、要现成的过渡动画——这三条正好是 Astro 的舒适区。**

## 六、什么时候该换

选型不是一劳永逸的。这几种情况我会考虑换：

- **文章上万篇，构建成了负担** → 迁 Hugo（或者给 Astro 加增量构建）
- **页面很简单，不想被框架绑住** → 纯手写或 Eleventy
- **团队本来就是 React 技术栈，还想要 SSR** → Next.js / SvelteKit 之类
- **只需要"能发文章"** → Hexo 或 Hugo 的上手成本比 Astro 更低

反过来，**如果站点有明确的设计感、需要一些交互、又希望首屏足够快，Astro 很难被替代**。

## 小结

把开头那三个问题写成一棵决策树：

```
需要组件化和一定交互吗？
├─ 不需要，只想写文章
│   ├─ 篇数多、追求极致构建速度 → Hugo
│   └─ 想要现成主题和插件     → Hexo
└─ 需要
    ├─ 首屏要快、JS 要少      → Astro
    └─ 要 SSR / 全栈 React    → Next.js、SvelteKit

完全不想被框架约束？
└─ 手写，或者只在个别环节（比如搜索索引）补个小脚本
```

**方案没有高下，只有"这一版的你到底想要什么"。**
这个博客当前这一版，想要的是"好看、快、能折腾"，所以是 Astro——就这样喵。
